# `packages/db/scripts/` — migration tooling

## `migrate.ts` — apply pipeline (M0)

Reads `packages/db/migrations/*.sql` in lexical order, tracks applied state
in a `schema_migrations` table, and applies any unapplied files via
[postgres.js](https://github.com/porsager/postgres). Runs once per `compose
up` as the `gatewerk-migrate` init container before `gatewerk-api` starts.

### Why this exists

Before M0 the deploy flow was `rsync source → docker compose up --build`.
Migrations had no apply step — they shipped to the source tree but the
schema only changed when an operator ran `pnpm --filter @gatewerk/db push`
manually against prod. That gap lets code depending on a new table deploy
without the table existing (the worker crashloops on `relation ... does
not exist` until someone pushes the schema by hand). M0 closes it by
making schema apply a hard prerequisite of API startup via
`depends_on: service_completed_successfully`.

### Behaviour

The script branches on first run:

- **schema_migrations does not exist + `templates` table exists** →
  established prod DB. Inserts every on-disk migration id into
  `schema_migrations` and exits 0 without executing any SQL. This is the
  one-time backfill for the migrations that had already shipped before
  M0 (the corpus is now at 27 migrations and growing; the test suite
  derives the count dynamically — the narrative count here is advisory
  and lags the on-disk truth by definition).
- **schema_migrations does not exist + `templates` does not exist** →
  truly fresh DB. Applies `packages/db/scripts/baseline.sql` (inside the
  advisory lock) to materialise the full schema, marks every corpus id
  lexicographically ≤ the `-- baseline-through:` marker in that file as
  applied, then falls through to the normal apply loop so any corpus ids
  added after the baseline was generated are executed as real migrations.
  This is what fires on a `git clone → docker compose up` install path.
  See **Baseline bootstrap** below for marker semantics and regeneration.
- **schema_migrations exists** → normal path. Skip ids already in the
  table, apply the rest, record one row per applied id.

### Baseline bootstrap

`packages/db/scripts/baseline.sql` is generated by
`pnpm --filter @gatewerk/db exec drizzle-kit export --sql` and represents
the full schema at a point in time. Its first line **must** be:

```
-- baseline-through: <last-migration-id-covered>
```

e.g. `-- baseline-through: 073_template_fields_snapshot`.

**When the branch fires:** `schema_migrations` absent AND `templates` absent
(a truly empty DB — no prior drizzle push, no prior deploy).

**What it does:**
1. Applies the baseline SQL to materialise the schema.
2. Marks every corpus id ≤ the marker as applied in `schema_migrations`.
3. Falls through to the normal apply loop — any corpus id that sorts
   *after* the marker is applied as a real incremental migration.

**Marker missing:** the script throws immediately with a descriptive error
rather than silently mis-classifying ids. Regenerating baseline.sql without
updating the marker will be caught on the next fresh-DB run.

**Regeneration:** run `pnpm --filter @gatewerk/db exec drizzle-kit export --sql`
and prepend `-- baseline-through: <new-corpus-max>` as the first line.
Advancing the marker is optional — a stale marker is not a correctness
problem; it just means more migrations apply on top of the baseline rather
than being pre-marked. Regenerate when a large batch of new migrations
would make the apply loop noticeably slow on first install.

### Concurrency

A pg session-level advisory lock (key `7423842`) guards the entire run.
Two parallel `compose up` containers can't race the apply because the
second one blocks on the lock until the first releases. The lock releases
on every exit path via `try/finally`, including hard failures — the
lock-contention failure-mode test in `migrate-script.test.ts` verifies this
by asserting `pg_try_advisory_lock(7423842)` returns true after a
broken-SQL run.

### `CREATE INDEX CONCURRENTLY`

Migrations 015, 016, 021, 022 use `CREATE INDEX CONCURRENTLY`, which Postgres
forbids inside an explicit transaction block. The script applies each
migration file via `sql.unsafe(text)` with no parameters — postgres.js
sends the file via simple-query protocol, which auto-commits each statement
individually, so `CONCURRENTLY` works correctly. Do not wrap individual
statements in `sql.begin(...)` from this script.

### Failure semantics

Exit 0 = success (apply, skip, or backfill). Exit non-zero = malformed SQL,
DB unreachable, missing `DATABASE_URL`, or any other fatal error. The
script logs each migration's id with `APPLY` / `SKIP` / `Backfilled`
prefixes for grep-friendly operator output.

### Local invocation

```bash
DATABASE_URL=postgresql://postgres:test@localhost:5444/postgres \
  bun packages/db/scripts/migrate.ts
```

For a sketch of the full set of env vars the prod compose stack expects
(DATABASE_URL, HMAC_SECRET, JWT_SECRET, UI_ORIGIN), see
`docker/.env.example`. The migrate script itself only reads `DATABASE_URL`
— the rest belong to gatewerk-api.

### What to do if a migration fails mid-deploy

The init container exits non-zero, `gatewerk-api` does not start (its
`depends_on` requires `service_completed_successfully`), and the deploy
fails fast. To recover:

1. SSH to the VPS and run `docker logs gatewerk-migrate` to see the failing
   migration id and SQL error.
2. Fix the migration SQL (or revert the offending commit) and redeploy.
3. If the migration partially applied, the migrate script will retry the
   same id on the next deploy — every migration in the corpus is written
   with `IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS` so reruns are safe.
4. If the migration cannot be re-run (rare; would need destructive DDL),
   manually `INSERT INTO schema_migrations (id) VALUES (...)` to mark it as
   applied and unblock the deploy, then patch the SQL for next time.

### Duplicate `009-*` migrations

Two files share the `009-` prefix:

- `009-template-status-and-token-version.sql`
- `009-template-status-token-version.sql`

Both exist because the same migration was authored twice with slightly
different filenames during early development; the duplicate landed before
the M0 pipeline existed to enforce uniqueness. The two files are
near-identical and use `ADD COLUMN IF NOT EXISTS` throughout, so applying
both is a true no-op on the schema.

The script tracks each filename as a separate id, so prod's
`schema_migrations` will hold both ids after backfill — that's intentional
and harmless.

**Do not consolidate them.** Two paths exist and both are bad:

- *Renaming* one file forces every operator who already applied the old
  name to manually backfill the new id (or face a re-run on next deploy).
- *Content-merging* into a single file is a subtle bug surface — the
  `schema_migrations` record diverges from the file on disk, and any
  follow-on cleanup commit looks innocuous in review.

A future cleanup ticket — **`consolidate-009`** — should align the
collapse with a coordinated backfill rebuild on prod (drop both rows from
`schema_migrations`, drop one file, re-run migrate.ts → backfill records
the survivor cleanly). Out of scope for v1.3.

**Going forward:** new migrations must not duplicate step numbers. The
lexical-sort apply order means a duplicate prefix produces a stable but
non-obvious ordering between the two; keep numbers monotonic.

### Backup

Postgres is external (Supabase managed), so backup is **not** a Gatewerk
operational concern in production. Retention, point-in-time recovery, and
nightly snapshots are handled by Supabase under the project plan; consult
the Supabase dashboard for the current retention window.

For local snapshots before destructive operations (e.g. a manual
`drizzle-kit push --force` against staging, or a one-off SQL fixup), take
a manual dump:

```bash
pg_dump "$DATABASE_URL" > "backup-$(date +%Y%m%d-%H%M).sql"
```

When to take a manual dump:

- **Before any major migration** that drops or rewrites data (rare; the
  M0 corpus is forward-only and additive by design).
- **Before destructive `psql` work** on prod (one-off remediation, hot
  fixes, schema_migrations row edits).
- **Before a cutover dry-run** on a staging clone.

### Rollback

Migrations are **forward-only**. The pipeline does not run a `down`
direction; the commented `-- DOWN` blocks at the bottom of each migration
file are operator references for manual rollback, not an automated path.

"Redeploy the prior image" works **only** if the landed migration is
backward-compatible:

- **Additive (safe):** new tables, new nullable columns, new indexes,
  new CHECK constraints on values prior code already wrote correctly.
- **Destructive (NOT safe):** drop column, type change, NOT NULL on a
  column the prior code wrote NULLs to, RENAME, or any other shape
  change the prior image's queries depend on. For these, a redeploy of
  the prior image will crash on `column does not exist` or similar.

For destructive migrations, recovery is a **forward-fix migration** that
restores the prior shape (or a compatible alternative), not a downgrade.

Rollback recovery checklist:

1. `psql "$DATABASE_URL" -c 'SELECT id, applied_at FROM schema_migrations ORDER BY id DESC LIMIT 5'`
   to confirm which migration just landed.
2. `docker logs gatewerk-api` to verify the symptom (column missing,
   constraint violation, etc.).
3. If additive-only landed: redeploy the prior image, file a forward-fix
   PR for the bug that surfaced.
4. If destructive landed: author a forward-fix migration, ship it
   through the normal `up -d --build` flow.

### Testing

`apps/api/src/__tests__/migrate-script.test.ts` covers six scenarios:

- Apply path against controlled SQL fixtures — fresh DB applies all,
  re-run skips all, deleting an id from `schema_migrations` re-applies
  only that id, including a fixture that uses `CREATE INDEX CONCURRENTLY`
  to verify simple-query protocol works.
- Production migration corpus against an established DB — bootstraps
  `templates`, runs script, verifies every on-disk migration id (count
  derived dynamically from `packages/db/migrations/`) is backfilled with
  no SQL execution, and that a second run is a clean no-op.
- Failure path — broken SQL throws and releases the advisory lock.

Tests gate on `TEST_DATABASE_URL`. Without it they skip with an actionable
message rather than failing.

```bash
docker run --rm -d --name gw-mig-test -e POSTGRES_PASSWORD=test \
  -p 5444:5432 postgres:16
TEST_DATABASE_URL=postgresql://postgres:test@localhost:5444/postgres \
  pnpm --filter @gatewerk/api test migrate-script
docker rm -f gw-mig-test
```
